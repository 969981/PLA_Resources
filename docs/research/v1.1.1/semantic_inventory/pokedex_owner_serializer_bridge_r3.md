# PLA 1.1.1 — R3 图鉴所有者、序列化镜像标志与保存任务的证据边界

> 独立增量研究文档。只读检查已发布的 Ghidra 12.2 C、原始 ELF 的已验证身份，以及 GitHub Actions 的完整静态扫描结果。**没有改写 ELF、Ghidra 工程、SQLite、NDJSON 或 82,731 份原始 C。**
>
> 本轮确认：**存在图鉴修改→保存任务的业务控制流，以及通用变更标记→内存复制→写文件的数据流；两条线尚未通过同一底层对象及同一序列化缓冲区闭合。**

- **OBSERVED**：大量别的结构也在 +0x298 保存不同数据。FUN_00AE676C、FUN_00AE6E18、FUN_00AE7090 确实直接对 +0x298 赋值，但没有定位到它们的 base 与 FUN_01148F20 的 context 同一。

## 2. 较新的实质进展 A：同一业务控制流中包含图鉴修改与保存任务

**OBSERVED — FUN_027DCC74（c/02/027dcc74.c）**：

1. 从 PTR_DAT_04379560 取得上层上下文，将其作为参数传给 FUN_01148F20，获得 Pokedex 相关对象 local_68。
2. 获取另一个受管理引用 FUN_01148F94(...), 处理命令/参数。
3. 在满足对象与状态判定时，以 local_68 作为第一个参数调用 **FUN_011325A0** 和 **FUN_011342B0**，触发真实图鉴字段修改。
4. 接着调用 **FUN_027DD040** 创建任务对象，将其放进 param_1[1]；该任务由 FUN_01145778 初始化并携带参数 3。
5. 后续通过 **FUN_011457E4** 推进任务，查询 FUN_011458D8 的完成状态，并清理任务。

**OBSERVED — FUN_011342B0（c/01/011342b0.c）**：

- 根据两个物种 ID 写入 state+0xDC+id*0x58 的标志 bit 0，更新 state+0x72 和物种记录+0x0C 的先后计数。
- 更新其他物种计数器；可写 state+0x1F440=0；调用 FUN_0113442C。
- 这是实在的图鉴内存写入，不是字符串命名证据。

**OBSERVED — FUN_011325A0（c/01/011325a0.c）**：

- 参数 1 也指向相同调用上下文中的图鉴状态对象。
- 写 state+0x1F440=param_2；写入多种按物种 ID*0x58 编址的记录；多处调用 FUN_0113442C。

**OBSERVED — 保存任务推进**：

- FUN_027DD040 → FUN_01145778：构建/初始化状态机任务。
- FUN_011457E4 → FUN_01148354 / FUN_01148558：提交异步工作；
- FUN_011457E4 → FUN_011485C0 / FUN_01148628 / FUN_01148690 / FUN_011486F8：等待、读取结果、执行提交包装及释放。
- FUN_01148690 → FUN_02A8F2F4 → nn::fs::Commit。

上述是**同一调用者内的业务控制流连接（CONTROL_FLOW_OBSERVED）**；但这仍不意味着 local_68 的记录字节已经经过某个具体的序列化描述符，或意味着 Commit 已成功执行。需补齐字节级别保存路径。

另外，FUN_0112527C 从某个对象的 +0x78 检查标志并 memcpy 0x2F1 字节，FUN_01125268 会清除该标志；这是独立的消息/缓存路径，**不能认作图鉴 Dirty**，也不可与 FUN_0112F528 的 state+0x78 总研究点数混淆。

## 3. 较新的实质进展 B：通用镜像描述符的复制标志和序列化

**OBSERVED — FUN_010CE5DC（c/01/010ce5dc.c）**：

- 遍历一批 stride=0x30 的数据描述符（从 manager+0x08 到 manager+0x10）。
- 每条描述符 +0x08 为待复制源指针；+0x10 为目标/镜像指针；+0x20 为复制长度；+0x28 为是否需要复制的字节标志。
- 仅在 +0x28 非 0 且源、目标指针非空时执行：memcpy(dst, src, len)，随后将此标志清零。
- 后续以描述符中的 32 位标识及数据长度依次写入输出流的虚函数接口。
- 使用 manager+0x80 与 +0xA0 互斥锁保护流程，并在部分阶段修改 manager+0xC1 标志。

**OBSERVED — 紧邻的通用写文件链**：

- FUN_010CE274 调用 FUN_010CE5DC；随后有 SHA-256 计算及文件句柄申请。
- FUN_010CE800 获取或创建写入句柄。
- FUN_02A8D6BC 调用 nn::fs::WriteFile；仅在其返回值为 0 时更新写入偏移/记录长度。
- 与另一条 FUN_02A8F2F4 → nn::fs::Commit 的控制路径在游戏中都存在。

**INFERRED**：描述符 +0x28 可暂标注为 PendingCopyFlag 或 SnapshotMirrorNeedsSync；行为与脏数据快照一致。

**UNRESOLVED**：没有证明这批描述符对应的 manager 是 PokedexSave 的所有者，也没有证明它包含任意一个 0x58-byte 图鉴记录，或能连接到相同的 Commit 事务。

**关键安全结论**：+0x28 清零发生在后续 WriteFile、Commit 成功验证之前，因此不能将清零等同于“已持久化”。必须寻找失败回退、重新置位或重建快照路径。

**重要反例**：FUN_005E58AC 也用 0x30 stride 并修改 +0x28 字节，但其源代码明确包含 gRPC slice 哈希表路径。这是另一种对象，**不能**凭 stride/偏移巧合并入游戏保存链。

## 4. 图鉴字段读取／拷贝的现有证据

- FUN_0112F528 更新 state+0x1E4CC+id*4 的打包研究任务状态。
- FUN_0140CD14 在已有 Ghidra C 中读取相同形式的 +0x1E4CC+id*4 字段。这是直接的业务层消费者，但不等于磁盘序列化。
- R3 扫描只出现 2 份 C 明文字面 +0x1E4CC；间接按寄存器偏移、指针别名以及整块 memcpy 读写不能由此排除。
- FUN_013F4074 与 FUN_0141308C 虽然同时调用 FUN_01148F20 并包含内存初始化（memset），但其所见操作是功能业务/UI 布局，当前不允许把它们标为 Pokedex Serializer。

**下一道最窄的技术关口**：

1. 以 FUN_01148F20 和全局 PTR_DAT_04379560 为根，在已恢复 Ghidra 工程中只读求解 context+0x298 写入者的实参来源及基址身份；优先检查间接调用、初始化构造函数和宽结构拷贝。
2. 以 FUN_010CE5DC 的源描述符（manager+0x08 迭代，每条+0x08 指针）为根，反向追踪描述符的注册者及源对象的大小/hash/ID。需要用 0x58-byte 图鉴记录的数据流证明同一身份。
3. 对镜像描述符 +0x28 标志做精确写入交叉引用，排除像 FUN_005E58AC 那样的同偏移不相关类型。
4. 以写盘句柄、提交任务 ID、底层返回码和成功/失败路径做确认；前置标志清零不算 Dirty committed。
5. 全程只使用已发布数据库和 ELF，**不做新的全量 Ghidra 分析**。

研究判断：本轮控制流和通用序列化链均已取得新证据，但二者尚未以同一对象字节和同一保存事务闭合，不能声称调用 UpdateAllReportPoke 就立即写盘。
